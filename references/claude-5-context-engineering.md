# Claude 5 上下文工程：少写常驻规则，让信息在正确时机出现

> 主要来源：[Anthropic《The new rules of context engineering for Claude 5 generation models》](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)。本文按 Longrein 关心的上下文分层与工程判断重新组织，不是逐字翻译。
>
> 作者：Thariq Shihipar，Anthropic 技术团队。原文发布于 2026-07-24；本文整理于 2026-07-27。

## 一、Prompt 只是上下文的一部分

Agent 收到的上下文不仅来自用户本轮 Prompt，还包括 system prompt、Skills、`CLAUDE.md`、memory、工具说明和任务 reference。Prompt 可以针对当前请求精确表达，上述材料却需要跨很多未知请求复用，因此更容易积累宽泛、重复或互相冲突的指令。

Anthropic 在 Claude Opus 5 和 Claude Fable 5 上重新审视 Claude Code 的上下文后，删除了超过 80% 的 system prompt，并称编码评测没有可测量的损失。这个结果不等于“提示词不重要”，而是说明强模型的主要瓶颈正在从缺少步骤说明，转向上下文是否清楚、分层正确、彼此一致。

## 二、先解除束缚，再增加指导

旧上下文常同时出现“按需要补文档”“不要加注释”等互相拉扯的指令。Claude 通常仍能推断用户意图，但必须花更多推理处理冲突，而且容易把过去为最坏情况编写的限制应用到并不适合的任务。

新模型能够更多地利用周围代码、当前请求和真实环境作判断。常驻规则应表达稳定目标和边界，而不是替所有未来任务提前决定局部做法。例如，比起永久规定不写多行注释，更可靠的规则是让新增代码匹配周围代码的注释密度、命名和惯例。

删除规则不等于取消安全边界。权限、破坏性动作、用户承诺和产品契约仍需要明确；应被删除的是没有稳定适用条件、与其他来源重复，或只是补偿旧模型缺陷的脚手架。

## 三、六组已经变化的实践

### 1. 从规则清单转向有边界的判断

过去通过具体禁令压住常见失败；现在先说明目标、权限和真实约束，让模型结合当前对象判断局部实现。只有错误后果重、适用条件稳定的领域，才值得保留低自由度规则。

### 2. 从示例驱动转向接口设计

旧模型常需要工具调用示例。对新模型，示例也会缩小探索空间，使它模仿某个调用形态，而不是根据任务选择最合适的参数。

更有效的做法是把工具、脚本和文件设计成自解释接口：参数表达真实选择，枚举体现状态空间，schema 说明约束，工具结果给出明确的成功、失败和继续方式。比如 Todo 工具的 `pending | in_progress | completed` 状态，以及“最多一个 in_progress”的契约，本身就在引导正确编排。

### 3. 从全部前置转向渐进披露

Claude Code 曾把 code review 和 verification 的详细规则常驻在 system prompt，因为关键时刻不能缺失。现在这些能力可以进入独立 Skills，只在相关任务中加载。

渐进披露也适用于工具和文档：工具定义可以 deferred loading；长 Skill 可以把具体协议和模板放入 references；`CLAUDE.md` 可以只保留入口和仓库特有陷阱，再指向按需读取的专业文件。目标不是隐藏信息，而是让当前任务只承担会改变当前判断的上下文成本。

### 4. 从跨层重复转向工具说明拥有工具契约

旧模型可能更依赖上下文尾部的提醒，因此 system prompt 与工具 description 会重复同一用法。新模型不再需要这种重复加权。工具怎么使用，优先由工具 schema 和 description 负责；system prompt 只保留产品级职责与权限。

每类信息应有一个权威来源。重复不仅浪费 Token，也会在一处更新、另一处过期时制造冲突。

### 5. 从 `CLAUDE.md` 记忆堆积转向专门记忆机制

过去用户会通过快捷方式把经验写入 `CLAUDE.md`。随着自动记忆、任务产物和 Skills 出现，仓库规则文件不再需要承担所有跨会话信息。

`CLAUDE.md` 应轻量描述仓库用途，并把主要篇幅留给无法从目录和代码直接看出的项目陷阱。个人偏好、运行经验、当前任务事实和专业工作流应进入各自的 memory、任务产物或 Skill，避免仓库规则成为无法修订的知识堆。

### 6. 从简单规格转向高保真 reference

新模型可以利用更复杂的 reference。规划不必局限于简单 Markdown：HTML 原型可以表达交互和视觉结构，真实代码可以表达行为语义，测试套件可以成为可执行规格，另一仓库的函数可以成为迁移参考，rubric 可以表达难以写成确定规则的专业品味。

reference 的价值是缩短语言描述与真实目标之间的距离。能提供代码、可运行测试或交互原型时，它们通常比抽象说明或截图更精确。

## 四、四类上下文各自负责什么

### System prompt

定义 Agent 所处的产品、基本职责、权限模型和运行方式。它是产品上下文，不应成为每项专业工作的总手册。只有构建自己的 Agent harness 时，才需要直接投入较多设计。

### `CLAUDE.md`

简要说明仓库用途，重点保存代码无法自行显露的项目惯例和陷阱。避免重复目录结构、通用编码常识或工具已有的说明。验证、评审等成体系的工作应由专门 Skill 承担，再从这里提供必要入口。

### Skills

作为轻量的专业指南，在需要时帮助模型找到团队特有的知识、判断方式和实践。除高风险、强契约领域外，避免把 Skill 写成穷举流程。内容较长时，用 references 和 templates 实现渐进披露。

### References

保存当前工作需要深入理解的规格、原型、代码、测试、rubric 和其他高保真材料。它们不必常驻，也不必被改写成长期规则；Agent 可以在相关任务中显式加载。

## 五、对 Longrein 的直接启示

Longrein 的常驻规则、Skills 和 references 应形成清楚的加载层次：

1. `global/job.md` 与 `global/soul.md` 只保留跨任务稳定的协作责任、证据观和权限边界。
2. `AGENTS.md` 保存当前仓库不能从代码直接推出的约定，不重复通用能力或工具契约。
3. Skill 定义何时介入、拥有什么专业判断、产物如何成为唯一当前来源；详细协议和模板按需放入 references。
4. 工具用 schema、参数和结果契约表达使用方法，不在多个提示层重复调用示例。
5. 任务规格优先使用代码、测试、HTML 原型和可执行输入等高保真 reference，不把所有语义压成抽象 prose。
6. 每次模型能力升级时，用代表性任务比较精简前后效果；没有证据证明仍有价值的旧脚手架应进入删除候选，而不是因为存在已久就继续常驻。

这篇文章最重要的判断不是“一律写短”，而是让每段上下文拥有明确责任：稳定边界常驻，专业能力按需加载，当前事实留在任务产物，高保真目标通过 reference 进入。上下文工程的质量取决于信息是否在正确的层级、正确的时机出现，而不是模型启动时看到了多少文字。
