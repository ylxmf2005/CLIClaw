# 测试证据链

本文件定义非平凡测试中 TestPlan、执行和 Test Report 如何共享一条风险与证据链。两份正式产物的结构分别以模板为唯一来源；本文件只定义判断责任。

## 一、TestPlan 先回答怎样才可能证明

先固定被测对象和现实条件：代码或构建身份、未提交差异、运行环境、路由、依赖、身份、权限、数据、可观察面与清理责任。旧报告、源码推断和作者说明可以帮助选测试，不能冒充本轮运行证据。

从 `context.md` 的承诺、原始缺陷、实际变化、公共契约、状态模型和受影响消费者形成风险。范围外的已知问题与当前 gate 分开；没有证据支持的通用极端情况不自动进入计划。

每个承重场景分配稳定用例 ID，并写清：

- 为什么要测，失败会伤害谁；
- 实际环境、身份和前置数据；
- 字面输入、请求或用户操作；
- 预期的用户结果与系统终态；
- 在哪里、多久、凭什么确认终态；
- 失败后影响哪些后续执行；
- 如何清理，以及通过后仍不能证明什么。

计划应允许另一位测试者直接执行，而不是让他现场补产品语义。执行前攻击计划：产品仍然错误时，是否存在全部用例变绿的路径；是否只验证触发，没有验证终态；是否遗漏旧调用者、权限、生命周期、异步消费者或恢复路径；是否用方便取得的信号替代真正的用户结果。

计划是当前风险模型，不是冻结的审批记录。真实执行、用户追问或实际 diff 暴露新风险时，更新同一 `test-plan.md`，保留稳定 ID，并让 `test-report.md` 的覆盖台账跟上。已经执行的旧场景不能静默消失。

## 二、执行把计划变成观察

先证明测试确实命中预期的版本、进程、数据和路由。对象无法确认且会改变结论时，只暂停依赖它的用例。

选择与承诺相同的入口。真实 UI 行为由浏览器证明；API、CLI、数据库、日志、审计、消息和外部接收方用于闭合对应层级。mock、stub、静态 schema 和代码阅读只支持它们实际覆盖的层级。

每个用例先保存动作和观察，再下结论。异步任务、回调、通知和调度要记录关联 ID、观察窗口、中间状态与最终来源。负向结论要说明观察了什么、多久以及“未发生”是否真的可证明。

`test-report.md` 是活的执行账本：第一项开跑时就建立，执行中持续更新用例状态、事实、失败和环境变化，最终再收敛为正式裁决。原始大材料进入 `evidence/`，但正文必须自包含地讲清动作、终态与证据边界。

用例状态：

- `passed`：直接证据支持完整预期；
- `failed`：实际行为与预期冲突；
- `partial`：已经执行，但缺少计划要求的步骤、终态、回读或清理证明；
- `blocked`：环境、权限、依赖或必要输入使其无法执行；
- `skipped`：经过风险判断主动不执行，并明确因此不能声称什么。

未执行不能静默消失。重跑保留每次结果和对应版本、环境；缺陷修复能够安全取得修前事实时，用同一输入证明修前失败、修后成立。旧证据只有在影响分析证明新变化没有触及其入口、路径、数据、依赖或终态时才能沿用，并在报告中说明理由。

## 三、Test Report 必须能够独立裁决

报告先固定实际被测对象，不把当前分支、后来提交或相邻环境的状态倒灌成本轮证据。若报告根据历史证据重建，要明确标注重建时间、证据完整度与不能恢复的细节，不能拿 TestPlan 的预期填补缺失执行记录。

覆盖台账中的每个 TestPlan ID 恰好出现一次。逐用例记录至少让读者看到：背景与风险、实际前置条件、预期、编号动作、实际响应与观察、终态回读、清理、证据入口和证据边界。只列 passed、命令名或附件路径不构成报告。

总体状态使用 `passed | failed | partial | blocked`：

- 所有承重结论都有直接证据才是 `passed`；
- 已确认产品行为违反承诺是 `failed`；
- 已取得有效证据但仍有承重缺口是 `partial`；
- 关键条件使整体无法形成有效判断是 `blocked`。

通过率不能掩盖关键失败。报告同时回答当前成果能否按既定承诺交付，并单列失败、未完成、证据薄弱、需要重测的范围、清理证明和仍保留的环境状态。

## 四、两份产物的权威边界

- `test-plan.md` 拥有当前风险模型、证明策略、用例与执行依赖。
- `test-report.md` 拥有实际执行、当前状态、最终裁决与证据解释。
- `evidence/` 保存原始材料，不拥有结论，不是第三份正式产物。
- `context.md` 只登记两份当前产物及任务承诺，不复制测试结论。

计划变化修订 Plan；执行事实和裁决变化修订 Report。不要维护平行摘要、handoff 文档或独立执行报告来争夺同一来源。

一次性 harness、fixture 和重放脚本默认属于本轮 evidence。要作为长期回归保护进入产品仓库时，它们变成实现资产，服从用户授权、项目规则和 `dev` 的责任。
