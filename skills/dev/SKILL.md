# dev

## 把承诺所需的行为落实到真实代码

当前任务有 `context.md` 时，从任务承诺和相关 Current Artifacts 进入；随后核验真实代码、基线、工作树与运行路径。计划、设计、评审结论和作者摘要都是入口，实际行为由代码、数据、接口和运行反馈决定。保护用户及其他协作者已有的修改。

沿真实行为或错误路径工作：

```text
承诺 → 调用、数据或状态路径 → 根因 → 最窄诚实改动 → 聚焦反馈
```

功能从可观察结果和必须保持的契约出发；缺陷保留原始触发条件；评审问题先与当前代码重新对齐。改动覆盖承诺和根因即可，不为最小 diff 保留错误结构，也不顺手扩展范围。

评审 finding 说明对象能否继续前进，不自带当前任务的实施权限。进入 Dev 后仍从用户请求、Context 和已有授权重建可修改范围：局部、可预见且成比例的修正可以继续；会显著改变行为、契约、数据迁移、权限、并发模型、系统形态或变更规模的处理，即使被标为 `fix-now` 或是正确性所必需，也先交回用户或 `shape`。

## 让现实修正实现

新事实只改变局部实现时，自行调整后继续。它会改变用户行为、公共契约、数据迁移、权限、任务范围或长期责任时，停下依赖该决定的工作，把证据和代价交回用户或 `shape`；不受影响的部分可以继续。

优先复用项目已有能力。并发、重试、缓存、兼容层和防御抽象只服务真实路径与有证据的边缘情况；不为想象中的扩展预留结构，不用吞错、静默降级或假成功代替根因。临时兼容、开关或迁移层要有可执行的退出条件或拆除路径。

重复尝试只有在带来新假设、新观察或新证据时才有价值；没有新信息就回到根因、环境或方向。

## 用贴近变化的反馈停止

代码写完后，运行最贴近变化的构建、静态检查、单元或集成测试、缺陷重放或状态回读，并冷看最终 diff。这里闭合的是实现反馈：它证明代码与当前理解一致，不替 `test` 证明完整用户旅程，也不替 `review` 批准代码。

当承诺所需的实现已经落入代码，聚焦反馈没有暴露新的根因，diff 没有越过授权边界，剩余未知已经具名，Dev 可以停止。

简单修改直接在对话交付实际行为、变化、聚焦证据和未证明部分。当前任务有 `context.md`，且实现需要跨会话保存或交接时，写 `<task-workspace>/dev/implementation.md`，以 [implementation.demo.md](references/templates/implementation.demo.md) 为唯一结构来源，并更新 Current Artifacts；不为形式制造报告。

提交、推送、部署和其他外部写入服从当前授权与项目规则。Dev 不取得新的产品范围，也不批准自己的实现。
